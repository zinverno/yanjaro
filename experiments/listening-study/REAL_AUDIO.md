## Почему сейчас нет троек

Из 90 возможных направленных сравнений десяти записей `eligible` оставил **64** после запрета одинаковой авторской группы. Их 3: Spring Spring (4), Joth (4), Juhani Junkala (2). Из 64: **56 — unknown tag coverage**, **8 — uncertain по текущим порогам**. Нет A/B/C/D пар, следовательно нет строгих троек и нечего утверждать или замораживать.

Правило тегов до screening: исходные положительные теги конкретной записи, только lower-case/trim, без добавления синонимов/инструментов из жанра и без отрицательных признаков. Альбомные/сборниковые hints сохраняются для проверяющих отдельно. Поэтому s03 не получает автоматически инструменты соседнего Judgement, s04 не получает выдуманный жанр, у o02/o03/u01/u02 инструменты неизвестны. Только s01/s02/o01/o04 имеют оба индивидуальных блока тегов. Нулевая выдача обусловлена и разметкой, и строгими акустическими порогами; она не подтверждает пригодность или бесполезность ритмического подхода.

Даже 14 успешно полученных файлов дали бы максимум floor(14/3)=4 непересекающиеся тройки; фактические 10 — максимум 3 по числу, но **0 по screen-v1**. Для 6 A/B + 2 C/D необходимы ≥24 записи и больше авторов. Предварительный конструктор оставляет пороги неизменными, запрещает повтор ID/hash и одного автора внутри тройки, ограничивает число записей автора четырьмя, sources двумя и разницу ролей A−B по автору до 1. Это детерминированный жадный preview, не доказанный максимум. При нулевой выдаче все эти ограничения выполняются тривиально, а не демонстрируют качество подбора.

## Локальная проверка

Новая команда создаёт **два автономных HTML-файла** вне Git. Реальные отрывки встроены локально; сервер, сеть, аккаунты и установка браузерных расширений не нужны. Файлы приватные (директория 0700, HTML 0600), не прикладывать их к PR, SurveyCircle или публичному хостингу. Экспорт в Git checkout отвергается. Существующий слепой интерфейс участников не изменён.

```sh
# Из experiments/listening-study; все пути ниже — ваши приватные локальные файлы.
python -m listening_study review-page "$PRIVATE_CATALOG" \
  examples/real-candidates.v1.json "$PRIVATE_REVIEW_DIR" --allow-real-audio
```

Владелец открывает `reviewer-1.html`, второй человек отдельно `reviewer-2.html`. Передайте второму только его HTML приватным способом, не его ответы первому до завершения независимой оценки. Это организационная независимость: без аккаунтов нельзя проверить личность проверяющего. HTML содержит только данные стимулов; другая оценка в него не встроена.

1. Сначала оценить каждую запись: ощущаемый BPM и half/double, ритм, энергию, слышимые инструменты/жанр, артефакты. Пусто — неизвестно. Отметить «подходит / не подходит / сомнительно» и причину.
2. Проверить o02 и флаги качества выше. Сомнение в происхождении или звуке — исключение/уточнение, а не скрытая правка метаданных.
3. В разделе сравнения доступны источник и два кандидата. **Свободные сочетания явно диагностические**, не называются прошедшими A/B/C/D. Повторы записи или автора не допускаются к оценке тройки. Сохранить отдельные оценки темпа/ритма/энергии/инструментов и отметку ошибочного сходства.
4. Нажать «Сохранить мой JSON». Черновик автоматически остаётся в локальном хранилище только своего reviewer-id и digest набора, если браузер его поддерживает; при отказе хранения показывается предупреждение. JSON можно импортировать в другой браузер своего проверяющего. Чужой reviewer-id или другой набор отклоняется. Перед закрытием убедиться, что файл сохранён.
5. Только после двух независимых JSON — совместный разбор расхождений. Экспорт всегда **PROVISIONAL**; он не выставляет `approved`, не обновляет `freeze`, не меняет признаки/пороги. При уточнении тегов, окна или алгоритма нужна новая явно описанная ревизия. На этом этапе никто не набирает участников и не использует ответы пилота.

Это наблюдение на текущей машине без отдельного бенчмарка; время получения файлов и браузерных проверок не входит. Дополнительный контроль готовых клипов измерен отдельно в JSON. Платных ресурсов не создано.
