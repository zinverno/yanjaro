# SDK metadata probe — дополнение к PR #12

Исходная точка: `49d381fc5bcbe8e9e95b9d306653e888b42ae193`, проверена на GitHub как HEAD открытого draft PR #12. Исходные `sample.json`, `results.json` и результаты listening pilot не изменяются. Дополнение находится только в этой папке и использует те же 30 ID в том же порядке.

## Запуск владельцем

По умолчанию probe проверяет только доступность SDK и exact application item в Secret Service. Он не читает секрет, не разблокирует keyring и не делает HTTP-запросов. Уже выполненный такой запуск записан в [agent-preflight.json](agent-preflight.json): `LOCAL_PERMISSION_DENIED`, стадия `DBUS_CONNECT`, errno `1` (EPERM). Секреты не прочитаны; запросов к Яндексу **0**. Это ограничение доступа из среды агента, не доказательство отсутствия входа у владельца.

Владелец может выполнить из своего обычного терминала Linux:

```sh
python3 /tmp/yanjaro-track-feasibility/experiments/track-feasibility/api-metadata/probe.py --owner-run --output /tmp/yanjaro-api-owner-20261015.json
```

В другом clone заменить только путь к скрипту. Probe использует уже установленный SDK 3.2.0 из окружения Python либо штатного `/usr/lib/yanjaro`, как launcher установленного Yanjaro. Ничего не устанавливает и не обновляет. Допустим запуск имеющимся Python из `.venv` проекта, где уже установлен SDK 3.2.0.

При доступном сохранённом входе появится приглашение ввести **`RUN 30`**. Это подтверждение локального запуска, не OAuth-токен. Секрет берётся внутри процесса из единственного item с `application=yanjaro`, `purpose=active-account-v1` в default collection. Токен не принимается из аргументов, stdin или переменных окружения; не выводится и не сохраняется. При locked keyring, отсутствующем/неоднозначном item или входе только в памяти плеера запуск останется BLOCKED. Память работающего плеера не читается. Логин, unlock, изменение и удаление credentials не выполняются.

Один вызов `Client.tracks()` → один `POST https://api.music.yandex.net/tracks`, только исходные 30 ID. Нет `Client.init()` / account-status: этот дополнительный вызов получает персональные данные аккаунта и для `tracks` не нужен. Нет fallback на другой API, endpoint, ID, регион или прокси. HTTP redirects, автоматические повторы, environment proxy/netrc, сырые логи отключены. Ответ должен быть JSON не более 2 MiB. Таймаут 8 секунд. При 401/403/429/сети — остановка без повторов и без удаления сохранённого входа.

Результат создаётся с правами 0600 и не перезаписывает существующий файл. До запроса сохраняется отметка о зарезервированном запуске; при аварийном завершении результат может остаться неизвестным. Не повторять автоматически. Передать для анализа можно **только созданный безопасный JSON**, не токен, cookie, debug log или вывод SDK. Для продолжения в этой сессии достаточно сообщить путь к файлу.

## Что установлено по существующему коду и SDK 3.2.0

Проверены фактические локальные исходники, а не предположения о последней версии. Копии SDK в native package и существующем venv имеют версию 3.2.0; проверенные `track.py`, `meta_data.py`, `client.py`, `utils/request.py` совпадают по SHA-256. Фактический перечень полей и хеши SDK записаны в `agent-preflight.json`.

Путь в приложении: `Controller._play_queue()` → `MusicApi.track_rows(ids)` → `client.tracks(ids)` → `track_model(track).row()`. У SDK это `TracksMixin.tracks` → `_BatchMixin._get_list('track', ...)` → `Request.post('/tracks', ...)` → `Track.de_list`. Метод делает один batch POST без предварительного account-status и без автоматических повторов. Probe использует тот же SDK-метод и его штатную десериализацию; дополнительный transport guard только сужает разрешённые запросы. Production adapter не редактируется и не запускается.

| Поле | SDK 3.2.0 | Что сохраняется / ограничение |
|---|---|---|
| `id` | Объявлено `str | int` | Запрошенный и реально возвращённый ID отдельно; сопоставление только по равенству ID |
| `title`, `artists` | Объявлены, значения могут отсутствовать | Название, artist ID и имя; без профилей и изображений |
| `duration_ms` | Optional integer | Миллисекунды или null; отсутствие не превращается в 0 |
| `albums` | Список Album | Все возвращённые Album ID/title/version/year/release_date/type/track_position; не только первый альбом |
| `version` | Optional string | Только реально возвращённая непустая версия; null не означает studio/original |
| `real_id` | Объявлено, семантика в SDK помечена TODO | Только внутренний идентификатор; не доказательство ISRC, master или эквивалентности |
| `matched_track`, `substituted` | Optional Track | Только вложенные ID; без следования ссылкам или повторного запроса |
| `meta_data` | Optional MetaData | Только album/version/year/volume/number. Это не гарантированно заполненный каталог; lyricist/composer и прочие поля не экспортируются |
| `isrc` | **Не объявлено в Track или MetaData** | null + `SDK_3_2_0_TRACK_ISRC_NOT_DECLARED`. Это ограничение интерфейса, не вывод об отсутствии ISRC на сервере |
| `available` | Optional boolean | true/false/null из ответа; не проверка фактического воспроизведения |

SDK `YandexMusicModel.cleanup_data` отбрасывает необъявленные поля. Probe не исследует сырой JSON в поиске ISRC и не меняет десериализатор. `real_id`, nested track IDs и Album ID остаются идентификаторами каталога; надёжного межкаталожного recording-level идентификатора только из наличия этих полей не возникает.

`track_model()` пригоден для UI, но не для полного исследования: сохраняет только первый альбом, переводит отсутствующую длительность в 0, неизвестную availability в false и не переносит version/real_id/matched_track/substituted/meta_data. Поэтому whitelist применяется к исходным SDK-моделям из того же `Client.tracks`, а не к сокращённым UI rows. Это проверено offline-тестом существующего `MusicApi.track_rows()`.

Полные SDK-модели никогда не сериализуются. Не сохраняются raw response, account UID, user_info, filename, storage_dir, URL обложек/потоков, заголовки, cookies, текст ошибки сервера, lyrics, normalization/R128. Ответ с данными пользовательской загрузки не экспортируется. Даже при ошибке исключение SDK не печатается: оно может содержать тело ответа и чувствительные данные.

## Наблюдаемый результат и сравнение с историей

На момент подготовки выполнен только реальный локальный preflight. Запуск владельцем и Yandex HTTP **NOT RUN**. Новые 30 строк с исходными ID и отдельными причинами BLOCKED находятся в [agent-preflight.json](agent-preflight.json). В каждой строке сохранён прежний статус, чтобы новый preflight не выглядел как регресс каталога.

| Вопрос | Фактический ответ |
|---|---|
| Реальные metadata HTTP-запросы | 0; не запускались агентом |
| Получены новые метаданные | 0 наблюдений / 30 не проверены через API |
| Длительность и конкретная версия | Не измерено, оба счётчика 0 при NOT RUN |
| ISRC | Не экспонируется этой SDK-моделью; серверное наличие не исследовалось |
| Надёжный recording/master ID | Не установлен; внутренние ID не получают такую семантику автоматически |
| Усиление MusicBrainz match | Новых доказательств пока нет |
| Предыдущие результаты | 13 METADATA_ONLY / 17 BLOCKED сохранены без изменений |
| Новый запуск | 30 BLOCKED из-за локального preflight; это не 30 отказов API |
| Акустические признаки | Не запрашивались; вывода о доступном источнике не прибавилось |

После реального запуска probe отдельно посчитает полученные metadata, duration, непустой **track.version** и их пересечение. Альбомная версия или текст в title не подменяют track.version. Batch-ответ не связывается с запросами по порядку: пропущенные, дублированные и неожиданные ID сохраняются как проблемы корреляции; `real_id` не используется как неподтверждённый redirect. Null/empty после SDK нельзя надёжно разделить на «сервер не прислал» и «сервер прислал null» — причина отражает это ограничение.

Offline comparison с историческими MusicBrainz-кандидатами показывает только совпадение title, разницу длительности и совпадение explicit Album ID cross-link, когда такие поля есть с обеих сторон. Он не копирует внешние значения в metadata Яндекса и всегда оставляет `recording_master_match=false`. Особенно полезны будущие ответы для «Команды» 149359136 (album 41194184, кандидат 2:54) и Blurry 70541 (кандидат album version 5:04, альтернативы radio edit). Даже совпавшие duration/version/release/ISRC были бы дополнительной поддержкой, а не самостоятельным доказательством одного master.

Предыдущий отчёт был неполон в выборе способа получения метаданных: веб-заглушки не устанавливают недоступность SDK API. Этот вывод исправлен уже анализом кода. Реальное улучшение покрытия можно утверждать только после owner-run, а не по наличию полей в dataclass или успеху синтетических тестов.

## Права остаются отдельной проверкой

Перепроверены [условия Яндекс Музыки](https://yandex.ru/legal/music_termsofuse/ru/) (публикация 25.08.2025), §§2.1, 2.6–2.8. Успешная авторизация или metadata response не предоставляют разрешения на массовое копирование каталога, обработку аудиопотока, хранение/коммерческое использование derived features. Для этих действий подтверждённого разрешения нет. Лицензия кода SDK также не лицензирует контент сервиса. Права на исходное аудио, модели и внешние признаки рассматриваются отдельно, как в исторической [матрице источников](../sources.json).

Технический блокер сейчас — D-Bus EPERM из agent context плюс отсутствие owner-run. Юридические блокеры — неподтверждённые права на дальнейшее копирование/обработку/коммерческое использование, независимо от будущего API-ответа. **Вывод о практически доступных акустических признаках не изменился**; API probe может улучшить metadata/crosswalk, но не получает аудио, embeddings или новые права.

## Проверки

```sh
python3 -m unittest discover -s experiments/track-feasibility/api-metadata -v
python3 -m unittest discover -s experiments/track-feasibility -v
```

10 новых тестов выполняются на реально установленном SDK 3.2.0 с синтетическим transport; живые запросы и секреты в тестах запрещены. Покрыты SDK-field whitelist, отсутствие ISRC, сохранение null/false, отбрасывание приватных полей, потеря данных в UI adapter, перестановки/дубликаты/неожиданные ID, единственный разрешённый batch, запрет иных запросов/аудио/повторов, preflight без чтения/разблокировки секрета, точный safe EPERM, локальный TTY gate и create-only output. Это проверка инструмента, не результат API-исследования.
