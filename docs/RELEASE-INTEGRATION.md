3. Переназначить **PR #2 на main**, проверить, что новые изменения начинаются после `8363c05`, затем merge commit.
4. Переназначить **PR #3 на main**, проверить, что изменения начинаются после `92cf26e`, затем merge commit.
5. PR **chore/public-release-prep → main** после принятия #3: workflow, AUR-рецепт, происхождение и документы. Слить обычным merge commit после проверки нового diff. До этого его review-база — `fix/previous-from-likes`.
6. Дождаться успешного workflow **на фактическом main**; сверить main с замороженным кодом и recipe. Если HEAD какой-либо ветки изменился, пересчитать план и проверки; не делать автоматический rebase/reset или force-push.

Это намеренно исходный коммит принятого пакета, а не новый merge HEAD с более поздним отчётом. Проверить peeled tag, реконструкцию исходника и SHA-256. Тег сейчас НЕ создан.
8. По отдельному разрешению создать GitHub prerelease и загрузить только файлы подготовленного release-каталога. Проверить анонимное скачивание каждого фактического asset, его SHA-256 и соответствие тегу. Ссылки добавить только после появления файлов.

Для этой уже связанной истории squash/rebase-merge не используем: они заменяют commit IDs и осложняют review следующих веток. Обычный merge сохраняет предков и не дублирует коммиты. Механика описана в [GitHub Docs](https://docs.github.com/en/pull-requests/reference/pull-request-merges). Существующие PR пока не переназначались и не выводились из draft.

[Машиночитаемые хеши/версии/digest](CI-release-rc4.json).
- **NOT RUN до разрешения:** реальные merge, CI на ещё не интегрированном main, тег, Release assets и их анонимное скачивание, AUR/Pamac. Эти границы не обходятся.
